## 1. What this product actually is

ChainOps AI is an **SRE control plane with an AI reasoning layer**, not a dashboard that
occasionally calls an LLM. Two things make it distinct from a generic SaaS admin:

1. **A coherent closed loop is the product.** Healthy → inject failure → metrics change →
   alert → incident → AI RCA → policy evaluation → remediation → verification → resolution →
   postmortem. Spec §49/§60/§73. Every phase must serve this loop.
2. **The simulation is the infrastructure.** There is no real Kubernetes or chain RPC in v0.
   The mock providers are the product's runtime, so they must behave like real systems:
   deterministic, time-scaled, stateful, with metrics that move *because* of events
   (spec §46–48, §72: "when something is simulated, make that explicit in the UI and architecture").

### The 80% trap the spec warns about

Sections §24, §25, §44–48, §49 are where fake versions of this product die: a timeline
component with hardcoded events, an "AI panel" with canned text, metrics that are random
per refresh. The spec explicitly forbids all three. The architecture answers:

- Timelines, AI analysis, incidents: **derived from the event log**, never hardcoded.
- Metrics: **generated by the simulation engine from simulation state**, not random per render.
- AI: **adapter over evidence-based deterministic reasoning**, labeled as simulated.

## 2. Binding decisions (the contract)

| # | Decision | Rationale |
|---|----------|-----------|
| D1 | **In-process simulation world.** A singleton `SimulationEngine` per server process is the source of truth for "live" telemetry and runtime state. It produces deterministic time-scaled series; repository-persisted entities (projects, deployments, incidents…) are the system of record for workflow state. | Spec §46 requires record-then-progress semantics; §48 requires causality (failure injection → metrics → incident). A time-series store is out of scope for v0; a deterministic generator with a seeded clock is not. |
| D2 | **Explicit state machines as a pure domain module.** Deployment and incident (and later experiment) transitions live in pure functions with table-driven guards. Route handlers and services may not invent transitions. | Spec §45. Testable without DB; unusable for impossible states. |
| D3 | **Adapters at six ports.** DeploymentProvider, RepositoryAnalyzer, ChainProvider, MetricsSource, AIService, PolicyEngine. One simulated adapter per port ships in v0; real integrations implement the same interface later. | Spec §3, §58 (abstractions only at real boundaries). |
| D4 | **Simulation determinism.** All randomness is seeded (`mulberry32`-style PRNG, seed = demo seed + entity id). Given the same seed and simulation time, series are identical. Demo reset restores the seed baseline. | Spec §46 "no random values on every page refresh". |
| D5 | **Event log as the spine.** `DomainEvent` is the append-only record of everything that happens (deployments, incidents, chaos, remediation, AI). Activity feed, incident timelines, postmortem drafts derive from it. | Spec §24 timelines must be generated, not authored. |
| D6 | **Every AI output is evidence-linked and policy-gated.** Analysis output shape: `{ confidence, hypothesis, evidence[], recommendations[] }`; remediation actions are allowlisted IDs validated by the policy engine; auto-execution only for configured safe actions. | Spec §25, §26, §56. |
| D7 | **REST + typed client, contract-first.** Consistent envelope `{ data, meta }` / `{ error: { code, message, requestId } }`; Zod schemas shared by route handlers and client; TanStack Query on the client. | Spec §61, §62. |
| D8 | **Simulated runtime is labeled.** A global `SimulationBanner` and a `/api/health` payload expose `mode: "simulation"`. No UI text claims real cluster/RPC control. | Spec §72. |
| D9 | **Dark-first design tokens, semantic status colors, no color-only status.** Status = icon + text + color everywhere. | Spec §9, §10, §51. |
| D10 | **Next.js App Router, TS strict, Server Components by default.** Client components only for interactivity; charts/logs virtualized or lazy. | Spec §4, §50. |
| D11 | **Business IDs (`DEP-1042`) + internal UUIDs.** Counters are per-type, monotonic, persisted with reset-to-seed on demo reset. | Spec §44, §64. |
| D12 | **Phases must leave the app runnable.** No phase ends with broken builds. Each phase = ship vertical slice behind the existing shell. | Spec §71. |

## 3. Tensions in the spec and how we resolve them

| Tension | Resolution |
|---|---|
| "Don't couple UI to providers" (§3) vs single Next.js app (§5) | Ports are TypeScript interfaces in `server/core/ports`; the composition root (`server/container.ts`) wires simulated adapters. Extracting to Go later means replacing `server/services` internals, not ports. |
| "Deterministic" (§46) vs "realistic delays" (§46) | Deterministic *content*, simulated *wall-clock progression*. The sim world runs on a virtual clock (accelerated 60×); deployment steps and incident phases advance against sim-time, so a 6-min deployment ≈ 6 s real. |
| "AI analysis" (§25) vs "no LLM available / no hallucinations" | v0 ships `HeuristicAIAdapter`: rule-based analysis over real telemetry evidence with explicit confidence; `LLMProvider` port exists for later. UI labels it "AI (simulated reasoning)". |
| "Information density" (§69) vs accessibility (§51) | Density via typography/spacing/borders, not color alone; every status pair has icon+text; charts ship `<summary>`/aria descriptions. |
| Perf (§50) vs live metrics everywhere | Dashboard uses one `/api/dashboard` aggregate endpoint, not per-widget calls; charts are client islands with stable props; logs paginate server-side. |
| "Production-quality" vs phase-based delivery | Phases ship thin-but-real vertical slices; depth is added phase by phase without re-architecture. |

## 4. Explicitly out of scope for v0

Real cluster/RPC/LLM integrations, multi-tenant auth with real SSO, real time-series DB,
horizontal scaling of the sim engine, mobile-native apps. The **interfaces** for all of these
exist; the **adapters** are simulated.

## 5. What "done" means for v0 (quality bar)

- The §60 E2E loop passes: create project → deploy → success → dashboard → inject RPC
  failure → incident → AI RCA → approve remediation → recovery → resolved → postmortem.
- Zero `any` outside generated/pragmatic edges, TS strict, unit tests for state machines,
  SLO/error-budget math, policy engine, anomaly thresholds.
- No page renders a hardcoded timeline, random-on-refresh metric, or unlabeled simulation.
